# 常态化制作流程

每期视频建立独立工作目录；本仓库保留流程，单期项目保存实际作品。可以把项目放在 `episodes/<slug>/`，并把大文件排除在 Git 之外。

| 阶段 | 负责人/工具 | 最小产物 | 通过关卡 |
| --- | --- | --- | --- |
| 0. 定义 | 制作者 | 选题简报 | 主题、受众、核心问题、时长、语言和交付形式明确 |
| 1. 调研 | 编剧／Codex | `research.md` | 每条上画面的事实有来源；未核实内容标为待核 |
| 2. 创意提案 | 编剧／导演／Codex | `concept-proposal.md`、选择记录 | 候选的切入点与镜头语言有实质区别；选定或已指定方向 |
| 3. 文案与隐喻 | 编剧／Codex | `narration.txt`、视觉隐喻 | 选定方向的因果主线、事实和预计时长可审 |
| 4. 导演计划 | 导演／Codex；video-craft 提供审阅建议 | `FilmPlan`、图解任务单 | Beat、共享对象、镜头焦点、相机起止和衔接均有定义，计划校验通过 |
| 5. 动态分镜 | Remotion；video-craft 审阅 | 10–15 秒低成本样片 | 运动、停顿、字幕区和连续性可直接观看；先修技术问题再审美 |
| 6. 图解与配音 | Anatomy、配音工具（按需） | 图解源码、音频、标记 | 机制可核、发音正确；定稿声音后重锁帧 |
| 7. 正式合成 | Remotion | Studio 预览、成片 | 同一 FilmPlan 驱动动态分镜与正式画面 |
| 8. 质检 | 导演／Codex + video-craft 建议 + 人工通看 | QC 记录、成片 | 事实、画面、字幕、声音、连续性和导出参数通过 |
| 9. 复盘 | 制作者 | `episode-review.md`、流程改动 | 只积累经过实际样片验证的做法 |

## 每期的工作顺序

### 0. 建立简报

填写 [`templates/episode-brief.md`](../templates/episode-brief.md)。先确定“观众看完能解释什么”，再选素材与图解。时长、语言和配音来源需在正式写文案前确定。参考作品只供选择与检验镜头方法；每期按自己的主题和受众决定画幅、风格与节奏。

### 1. 调研与创意提案

收集可靠出处。每个数字、术语和人名都能回指 URL 或明确的原始资料。用 [`templates/concept-proposal.md`](../templates/concept-proposal.md) 先比较三种有实质区别的切入点、开场文案、认知变化和镜头语言；方向已由用户指定时直接记录选择。选定后才写完整解说词，维持一个贯穿例子；章节标题要能直接说明本章内容。提案不写精确帧数，配音、字幕和质检使用本项目自己的流程及授权适合的工具。

### 2. 分镜与图解选型

从选定方向写观众认知变化的 beat，再写共用世界和对象，最后决定镜头。镜头按画面单元切分，不机械地一句一镜；每镜写明焦点、起止构图、相机路径、停留和下一镜承接的对象。结构与边界检查见 [`film-plan.md`](film-plan.md)。用 video-craft 对照简报审阅叙事钩子、主焦点、信息层级和运动目的；只采纳能指出具体问题与改法的建议，不套用固定风格或秒数。遇到“内部如何工作”的关键机制，再给 Anatomy 写图解任务单；输出要能转为确定的 SVG 或帧序列。

### 3. 配音、合成与预览

先用占位文字和几何图形做 10–15 秒动态分镜。Remotion 项目只使用一个帧率和一份 FilmPlan；先看运动节奏、镜头承接和可读性。定稿配音后更新标记并重验镜头对位，不能只挪字幕掩盖错位。正式合成仍先看代表片段，再扩展到全片。

### 4. 质检与归档

按下表检查，并填写 [`templates/episode-review.md`](../templates/episode-review.md)。质检问题分为阻断交付、可修复的小问题和已接受的限制。把结论链接回分镜或时间轴，方便下次定位。

| 检查项 | 判定方法 |
| --- | --- |
| 事实 | 逐项核对研究记录；示意数据明确标“示意” |
| 声音与字幕 | 听看全片，检查漏字、错字、发音、字幕同步及遮挡 |
| 画面 | 一个主要视觉焦点；图解读数与动作一致；图解与字幕不互相压住 |
| 节奏 | 重点入场有时间理解；画面动作服务解说；章节衔接有承接 |
| 连续性 | 镜头交界无空帧、突变和声音断裂 |
| 导出 | 实际文件能播放；分辨率、帧率、时长和音量符合简报 |

## 改进循环

每次只把**已在实际项目中验证**的规则写回主流程。新建议先在贡献记录里说明：原问题、发生在哪个镜头或阶段、改动、前后证据、适用边界。下期再用同一检查项确认改动是否有效。
